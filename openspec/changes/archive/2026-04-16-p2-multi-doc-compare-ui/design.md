## Context

当前系统的问答流程是"单文档"模式：用户选择一个文档 → 进入该文档的 chat 页面 → 问答的 doc_id 固定为该文档。P2-6 要求扩展为"多文档"模式，让用户能同时选择多份文档进行跨文档问答。

Python 侧 P2-2 将提供多文档联合检索能力，前端 `/api/ask` 请求的 `doc_id` 会扩展为 `doc_ids` 数组。在 Mock 模式下，前端可独立模拟多文档引用。

现有架构中，ChatSession 通过 `documentId` 外键关联单个 Document。需要扩展此关系以支持多文档。

## Goals / Non-Goals

**Goals:**
- 用户能从已索引文档中选择 2+ 份文档，进入多文档问答模式
- 问答结果中的引用能清晰标识来源文档
- 引用面板能按文档分组展示引用
- Mock 模式下能完整模拟多文档问答流程
- 数据库层面支持多文档 session

**Non-Goals:**
- 不实现文档间的自动关联推荐（"你可能还想加入这份文档"）
- 不实现跨文档的结构对比或 diff 视图
- 不修改 Python 侧接口（仅对接 P2-2 定义的接口）
- 不实现文档权限控制

## Decisions

### 1. 多文档 Session 的数据模型

**选择**: 在 ChatSession 中使用 JSON 字段 `documentIds` (string[]) 存储关联的文档 ID 列表，保留原 `documentId` 字段作为"主文档"向后兼容。

**理由**: 比引入多对多中间表更简单，SQLite 支持 JSON 查询。ChatSession 的文档列表在创建后不会频繁变更，不需要关系型建模的灵活性。

**替代方案**: 
- 多对多关系表：更规范但增加复杂度，对于最多选择 5-10 份文档的场景过度设计
- 逗号分隔字符串：不够类型安全

### 2. 多文档入口交互

**选择**: 在文档管理页增加"多文档问答"入口按钮。点击后弹出 Dialog，用户勾选文档（checkbox），确认后跳转到多文档 chat 页面。

**理由**: 
- 与现有单文档问答入口（文档卡片上的"开始问答"按钮）并行，不破坏现有流程
- Dialog 选择器比内联多选更清晰，能展示文档状态确保只选已索引的文档

### 3. 多文档 Chat 页面路由

**选择**: 使用 `/chat/multi?docs=id1,id2,id3` 查询参数路由，而非新的动态路由段。

**理由**: 文档数量不固定，用 query param 比 path param 更灵活。避免与现有 `/chat/[documentId]` 路由冲突。

### 4. 引用来源区分

**选择**: 在 Citation 类型中增加 `documentName` 字段，引用标记 `[1]` 旁显示文档名缩写色标（如 `[1] 📄A`），引用面板按文档名分组为 Accordion。

**理由**: 用户在多文档模式下最需要知道"这个引用来自哪份文档"。颜色标签 + 分组是最直观的方式。

## Risks / Trade-offs

- **[Python P2-2 接口未就绪]** → Mock 模式下模拟多 doc_id 请求和多来源引用，确保前端可独立开发。接口就绪后仅需在 Route Handler 中切换转发逻辑。
- **[文档选择上限]** → 不设硬性上限但 UI 上建议 2-5 份。过多文档的联合检索质量和性能由 Python 侧控制。
- **[Session 迁移]** → 新增 `documentIds` JSON 字段为可选，现有单文档 session 无需迁移。
